# muse-2-api-bridge (muse-serve)

**Your Muse agent, as an OpenAI-compatible model for OpenCode — with file-backed memory per session.**

Point OpenCode at a tiny server on your agent's machine. The server speaks
OpenAI's protocol, routes each request to a **session**, extracts only the
**delta** (what's new since the last turn), and wakes a worker agent that
reasons over the delta plus a bounded history tail — then writes back an
OpenAI-shaped reply. Session memory lives in `data/sessions/<id>/history.json`,
so later turns remember everything without re-ingesting full history. You get
an agent with live memory and judgment behind OpenCode's local tools — no
per-token API bill, no model swap.

```
OpenCode (your PC) ──Tailscale──▶ server.py ──▶ session router ──▶ worker (hook-woken)
                                        ▲         (deterministic)      │
                                        │                            │ reads dispatch
                                        └──── response file ─────────┘ (delta + history tail)
```

## How it works (60 seconds)

1. OpenCode sends a normal `POST /v1/chat/completions` (streaming or not).
2. The server identifies the **session** deterministically — an explicit
   session id if the client sends one (`X-Session-Id` / `X-OpenCode-Session-Id`
   headers), else a prefix-hash match on `messages[]`, else a recency fallback
   (covers `/compact`) — extracts only the **delta** (what's new since the
   last turn), and writes `data/dispatch/<id>.json` with the delta, the
   session's last 10 messages (`history_tail`), and the tools block.
3. A hook notices the queued request and wakes a **worker** agent, which reads
   the dispatch file, reasons over delta + history tail, and writes
   `data/responses/<id>.json` atomically. The worker makes content decisions
   (text, tool calls, or both); it never executes client tools itself.
4. The server validates the answer and returns it — real SSE chunks for
   streams, a normal JSON body otherwise.
5. OpenCode executes any `tool_calls` locally and sends results back as the
   next request. Standard agentic loop.

Session memory is `data/sessions/<id>/history.json` — every turn appends the
delta, so context persists across turns and across restarts. See
`docs/ARCHITECTURE.md` for the full design and failure-mode table.

## Configuration

`config.json` (generated by the installer; a template is `config.json.example`):

| Key | Default | What |
| --- | --- | --- |
| `project_name` | `jarvis-serve` | User-visible strings (logs, `/v1/models`) |
| `agent_name` | `assistant` | Name used in the worker contract |
| `session_id_header` | `X-Session-Id` | Request header used as explicit session id |
| `session_id_field` | `null` | Top-level body field used as explicit session id |
| `recent_window_secs` | `120` | `/compact` fallback: join the most recent session if active within this window |
| `session_idle_secs` | `86400` | Idle sessions eligible for archiving |
| `tool_desc_max_chars` | `200` | Tool descriptions truncated to this |
| `seed_template` | `agent/seed.md` | (retired in v1.5; kept for history) |
| `log_wire_keys` | `true` | Log header names + body keys per request (no values) |

## Install

**On the agent's machine** — the agent itself runs this (see `agent/SKILL.md`
for the exact sequence):

```bash
git clone <this-repo> && cd jarvis-serve
bash scripts/install.sh        # dirs + token + config + systemd, then health check
# then: hook script -> hooks.add -> dry_run -> enable -> curl end-to-end test
```

**On your PC** (`opencode.json`, see `opencode/opencode.json.example`):

```json
{
  "provider": {
    "jarvis-serve": {
      "npm": "@ai-sdk/openai-compatible",
      "options": {
        "baseURL": "http://<TAILSCALE-IP>:8765/v1",
        "apiKey": "<TOKEN-FROM-INSTALL>"
      },
      "models": { "muse-agent": { "name": "Muse Agent" } }
    }
  }
}
```

Then pick `muse-agent` as your OpenCode model. Send `X-Session-Id` (or
`X-OpenCode-Session-Id`) per conversation for deterministic session routing.

## Reaching the server when the VM can't accept inbound connections

Some agent VMs join Tailscale as client-only: they can dial out but nothing
can dial in. For that case, run the reverse tunnel on the agent VM:

```bash
python3 scripts/reverse-tunnel.py --remote-host <PC-TAILSCALE-IP> \
  --ssh-user <PC-USER> --ssh-key ~/.ssh/<key>
```

This opens `PC 127.0.0.1:18765 → VM 127.0.0.1:8765` over SSH (host key
pinned, auto-reconnect with backoff). OpenCode on the PC then uses
`baseURL: http://127.0.0.1:18765/v1` — its own loopback. The tunnel is a
plain background process: if the VM restarts, restart it.

## Honest limitations

- **Streaming is emulated** — pause, then burst. No typewriter effect.
- **Seconds per turn** — hook claim (\~0.1s) + worker spin-up + inference.
  Measured \~6s (simple) to \~15s+ (heavy reasoning). Worker cold-starts every
  turn; there is no warm persistent agent in the serving path.
- **Session matching is heuristic** without an explicit client session id:
  prefix-hash on `messages[]` with a recency fallback for `/compact`. Send
  `X-Session-Id` for deterministic routing.
- **Serial per session** — requests for the same session are serialized by
  the server; different sessions run in parallel.
- **Plan usage** — every served turn is a real agent execution on the
  account's plan. Don't point a 200-turn coding session at it blindly.
- **Trust boundary** — bind is Tailscale/loopback by default. Don't expose
  the port to the open internet; the bearer token is the only auth.
- **Identity** — the worker never mentions jarvis-serve or the bridge
  machinery; it identifies as a Muse agent.

## Security

- Bearer-token auth on all `/v1/*` routes; only the SHA-256 of the token is
  stored (`config.json`, mode 600). Constant-time comparison.
- Request bodies capped at 8 MB. Tokens never logged.
- Worker output is validated before anything reaches the client; malformed
  output becomes a `500` error object, never a hang or a crash.
